# Porting Unity ML-Agents v0.4 to a modern Python stack

The Udacity Navigation project ships a Unity environment built in 2018 against
`unityagents==0.4.0`, whose `requirements.txt` pins:

```
tensorflow==1.7.1   torch==0.4.0   protobuf==3.5.2   grpcio==1.11.0
```

and whose setup instructions begin *"Create an environment with Python 3.6."*
Python 3.6 reached end of life in December 2021. None of those four packages
installs on a current interpreter.

Rather than install a dead Python, this repository **vendors the ml-agents v0.4
client into `vendor/` and modernises it**. The result runs on Python 3.11 with
PyTorch 2.14, gRPC 1.83 and NumPy 2 — and, after the fourth fix below, runs six
environments in parallel at full speed.

The whole port is four changes. Three are documented below as patches to
vendored code; the fourth is a lesson about how the Unity player behaves.

---

## 0. What could simply be deleted

`unityagents` imports `numpy`, `PIL`, `grpc` and its own protobuf stubs. It
never imports TensorFlow anywhere:

```
$ grep -rn "tensorflow" vendor/unityagents/
(no matches)
```

TensorFlow 1.7.1 is a dependency of Unity's *trainers*, which this project does
not use — we only need `UnityEnvironment`, the client. Dropping it removes the
single hardest pin to satisfy, at no cost.

**protobuf**, by contrast, cannot simply be unpinned. The stubs in
`vendor/communicator_objects/*_pb2.py` were generated by protoc 3.5, and the
protobuf runtime from 4.21 onward refuses to load descriptors built by
generators older than 3.19. Pinning `protobuf==3.20.3` — the last release that
still accepts them — avoids regenerating stubs from `.proto` sources that the
course repository does not ship. Modern `grpcio` works against it unchanged.

## 1. `np.float_` was removed in NumPy 2.0

**Symptom** — the environment connects, reports its brain correctly, then dies
on the first `step()`:

```
AttributeError: `np.float_` was removed in the NumPy 2.0 release.
Use `np.float64` instead.
```

**Cause** — three `isinstance` checks in `environment.py` name the removed
alias. `np.int_` alongside it still exists in NumPy 2, so only one alias is
actually affected.

**Fix** — `np.float_` → `np.float64` at `environment.py:287,299,409`.

---

## 2. A shared `Pipe()` makes concurrent environments impossible

**Symptom** — two `UnityEnvironment` objects in one process cross-talk and
deadlock.

**Cause** — a real bug in ml-agents v0.4. The gRPC servicer declares its pipe at
*class* scope, so every instance in the process shares one pair of connections:

```python
class UnityToExternalServicerImplementation(UnityToExternalServicer):
    parent_conn, child_conn = Pipe()          # class attribute!
```

Each environment's replies are therefore delivered to whichever environment
happens to read first.

**Fix** — move the pipe into `__init__` so each servicer owns its own:

```python
class UnityToExternalServicerImplementation(UnityToExternalServicer):
    def __init__(self):
        self.parent_conn, self.child_conn = Pipe()
```

`RpcCommunicator.initialize` already constructs the servicer per communicator
and reaches it through `self.unity_to_external`, so nothing else changes.

## 3. Detecting a free port on Windows (a bug in *our* code, not Unity's)

`worker_id` maps directly onto TCP port `5005 + worker_id`, with no collision
handling: a leaked process from an earlier run makes the next one fail with the
misleading message *"worker number 0 is still in use."* So `env.py` probes for a
free port first. The obvious probe is wrong on Windows in two independent ways:

* **`SO_REUSEADDR` means the opposite of what it means on Unix.** On Linux it
  permits rebinding a socket in `TIME_WAIT`; on Windows it permits binding a
  port that is *actively bound by another socket*. A bind test that sets it
  therefore succeeds against a live listener and reports the port free.
* **Address families must match.** gRPC binds `[::]` (IPv6 dual-stack); a naive
  probe binds IPv4 `0.0.0.0`. On Windows those need not collide, so the probe
  passes and the gRPC server then dies with `WSAEADDRINUSE`.

Observed directly — nothing listening on 5009 by the probe's reckoning, while
`netstat` showed an established connection on it:

```
Failed to add port to server: No address added out of total 1 resolved for '[::]:5009'
(bind: WSA Error (Only one usage of each socket address ... is normally permitted.))
```

**Fix** — probe by *connecting*, not binding. A successful `connect_ex` is
unambiguous proof that something is listening, and it is address-family
explicit. See `_port_is_free` in `src/banana_nav/env.py`.

## 4. `unity-environment.log` silently serialises parallel runs

This is the one worth knowing about, because it produces no error at all.

**Symptom** — launch four training processes with distinct ports. All four Unity
players start. All four complete the gRPC handshake and report their brain
parameters. `netstat` shows four established connections on four different
ports. Then **exactly one** run makes progress; the other three sit connected
and idle indefinitely. No exception, no timeout, no log message. Which run wins
varies between attempts.

**Cause** — the Unity player writes `unity-environment.log` into its *process
working directory* and holds the file open. `unityagents` launches the binary
with `subprocess.Popen` without setting `cwd`, so every player inherits the
launcher's directory. Point four players at one directory and they contend for
one log file.

Two red herrings cost real time before this surfaced. Neither was the cause:

* *Port collisions* — plausible, and there genuinely was a port bug (§3), but
  fixing it changed nothing here.
* *Thread oversubscription* — PyTorch sizes its pool to the core count, so four
  trainers spawn ~32 threads competing with four busy-spinning Unity
  `-batchmode` processes on 8 logical cores. A real problem worth fixing, and
  `limit_torch_threads()` still does, but it was not this problem.

**Fix** — give every run a private working directory. `cmd_ablate` creates
`results/<study>/_rundirs/<tag>/` per run and passes it as `cwd`.

**Measured effect** — two environments, same machine, 300 steps each:

| Configuration | Throughput per env |
|---|---|
| One environment alone | 191 steps/s |
| Two environments, shared `cwd` | one runs, one hangs forever |
| Two environments, private `cwd` | **191 steps/s each** |

Parallel environments cost essentially nothing once they stop fighting over a
log file. Scaled to the full study on an 8-core machine:

| Workers | Aggregate throughput |
|---|---|
| 4 | 1.20 episodes/s |
| 6 | 1.53 episodes/s |

## What is *not* patched

* **The time scale is baked into the Unity build.** v0.4's Python side never
  sends an `EngineConfiguration`; `_generate_reset_input` only sets
  `rl_in.is_training`, a boolean the Academy uses to choose between the
  training and inference configurations stored *in the build*. There is no way
  to raise the simulation speed from Python, which is why parallelism is the
  only lever on total training time.
* **The protobuf stubs.** Pinning `protobuf==3.20.3` is a deliberate trade: it
  keeps the vendored stubs byte-identical to Udacity's, so this environment
  stays verifiably the one the project requires. Regenerating them from
  upstream `.proto` sources would lift the pin, at the cost of that guarantee.

## Reproducing the port

Everything above is already applied in `vendor/`. To verify against a pristine
copy, diff it against `python/` in
[udacity/Value-based-methods](https://github.com/udacity/Value-based-methods):

```bash
diff -ru path/to/Value-based-methods/python/unityagents vendor/unityagents
```

You should see exactly the changes in §1 and §2.
